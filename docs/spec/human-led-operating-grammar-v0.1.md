## Purpose

The **Human-Led Operating Grammar** names the bridge between human expression and governed machine action.

It explains how human meaning becomes machine-operable without becoming machine authority.

This artifact is a translation layer between:

```text
Language / intent
-> Architecture / roles
-> Runtime governance
-> Market / ecosystem positioning
```

It does not add a new authority layer. It gives clean language to the roles and transitions already present in ONE/RIO/MUSS.

---

## One-line definition

The Human-Led Operating Grammar is the translation layer that keeps machine operation inside human authority.

---

## System sentence

ONE/RIO/MUSS is not only an operating environment. It is a human-led operating grammar: a way for human meaning to become machine-assisted action only through translation, governance, fidelity checks, and proof.

## Why this matters

The runtime MVP proves the mechanism:

```text
Agent cannot call tool directly
-> agent must propose packet
-> PDP/RIO evaluates
-> Sentinel/PEP enforces
-> MUS receipt records
```

The Human-Led Operating Grammar explains the same pattern in human terms:

```text
Expression is not instruction.
Translation is not authorization.
Proposal is not approval.
Capability is not permission.
Execution is not authority.
Proof is not wisdom.
Receipt is not the person.
```

This lets people understand the architecture without first needing to understand PDP, PEP, hash binding, JSON schemas, Ed25519, or runtime conformance.

## Core mapping

| Layer | What it does | Boundary |
|------|--------------|----------|
| Human expression | Meaning, need, intent, concern | Not yet action authority |
| Bondi / Scribe | Translates into structured intent | Cannot approve |
| Action Packet | Makes proposed action inspectable | Packet is not permission |
| RIO / PDP | Decides admissibility under policy and authority | Governance boundary |
| Sentinel / PEP | Enforces exact match between authorization and execution | Cannot improvise |
| MUS | Produces receipt | Proof, not wisdom |
| Ledger / Chronicle | Preserves record | Memory, not authority |
| MANTIS / Coherence | Watches patterns, drift, recurrence, instability | Signal, not verdict |
| Human | Source of authority | Final commit / revocation |

---

## Translation path

```text
Human expression
-> Scribe/Bondi translation
-> structured intent
-> inspectable packet
-> RIO/PDP admissibility review
-> human commit where required
-> Sentinel/PEP execution-fidelity gate
-> controlled execution
-> MUS receipt
-> Ledger/Chronicle record
-> MANTIS/Coherence observation
-> human calibration
```

The critical rule is that no translation step becomes authority. Translation makes intent legible. It does not grant permission.

## Runtime mapping

The runtime MVP can be read as a mechanical enforcement of the grammar.

| Grammar rule | Runtime expression |
|-------------|-------------------|
| Expression is not instruction | Raw user/model text must be translated before consequence |
| Translation is not authorization | Scribe/Bondi output cannot execute |
| Proposal is not approval | Proposal packet requires review/commit path |
| Capability is not permission | Tool availability does not imply allowed use |
| Execution is not authority | Execution adapter acts only under token/gate |
| Proof is not wisdom | Receipt records event, not moral correctness |
| Receipt is not the person | Ledger preserves event, not human identity |

## Market bridge

Human-in-the-loop is not strong enough language for this architecture.

Human-in-the-loop often means a person is inserted somewhere into an otherwise machine-led process.

Human-Led Operating Grammar means the entire action path is grammatically structured so human authority remains primary from expression through consequence.

| Common phrase | Limitation | Human-Led Operating Grammar correction |
|--------------|------------|-----------------------------------------|
| Human-in-the-loop | Human may be a checkpoint inside machine flow | Human remains source of authority |
| AI assistant | Helpfulness can drift into authority | Machine operation remains bounded |
| Agentic workflow | Capability can become action | Capability requires permission and proof |
| Audit trail | Often post-hoc only | Governance and proof happen before/during/after consequence |
| Personal AI | Can blur identity and representation | It may operate for the human; it may not become the human |

## Relationship to Embodied Co-Regulation

When the system moves into robots, exosuits, prosthetics, homes, schools, streets, shelters, or workplaces, the grammar must still hold.

Physical-world translation:

```text
Human need
-> physical assistance proposal
-> local governance and safety review
-> bounded machine movement
-> receipt or event log
-> human/community review
```

Embodied systems must preserve the same non-collapse rules:

- assistance is not command;
- presence is not authority;
- routing is not coercion;
- support is not surveillance;
- augmentation is not control.

## Economic extension: Creation Trust / Perpetual Creation Flow

The Creation Trust or Perpetual Creation Flow can be understood as an economic application of the same operating grammar.

Runtime grammar:

```text
Generated action
-> pause
-> governance
-> consequence
-> receipt
```

Economic grammar:

```text
Generated value
-> pause
-> stewardship
-> human capability
-> record
```

The careful boundary:

> The Creation Trust applies the operating grammar economically; it is not required for the core runtime to function.

This keeps the economic layer parallel to the runtime architecture rather than making it a core invariant.

## Failure modes

| Failure mode | Description | Control |
|-------------|-------------|---------|
| Grammar collapse | A non-collapse rule is ignored, e.g. proposal treated as approval | RIO review / failure-mode catalog |
| Translation authority drift | Scribe/Bondi output becomes treated as permission | Explicit proposer/approver separation |
| Market simplification drift | Public explanation becomes too loose and overclaims | Claim-status and public/private review |
| Runtime jargon lockout | Explanation requires too much technical detail | Human grammar layer |
| Economic layer overreach | Creation Trust is treated as core runtime requirement | Parallel application boundary |
| Relationship override | Trust/attunement rewrites non-collapse grammar | Adaptive Trust Envelope limits |
| Proof-person collapse | Receipts become the person or identity | Proof/person boundary |
